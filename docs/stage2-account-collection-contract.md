## 1. 三个必须先定的决策

这三条不定，下面所有接口都没法实现。每条给推荐值与理由，**结论以负责人确认为准**。

### 1.1 账号从哪里来（阻塞项，且与现有验收文档冲突）

| 方案 | 做法 | 定位 |
| --- | --- | --- |
| **B. 复用来源站身份（目标）** | 用户在来源站完成登录，平台只持可撤销令牌（OAuth 授权码，令牌交换由平台后端代理，client_secret 永不进 App / 浏览器） | **目标形态**：来源网站已有用户时，客户端优先用来源站身份（定位 §4.2、阶段 1 铁律 2）；平台不持有用户密码 |
| A. 平台自建（过渡 / 兜底） | 平台自己存账号与密码哈希，登录只对平台 | **过渡 / 兜底**：用于来源站身份授权尚未接入、或账号绑定实现尚未落地的阶段；不是产品终态，必须预先设计切换路径（账号映射 + 收藏迁移） |

**目标 = 方案 B（复用来源站身份），过渡 = 方案 A（平台自建）**。首站 Otaku 已于 2026-10-24 由站主定稿标准 OAuth 授权端点（`/oauth/authorize` → `POST /api/auth/token` → `GET /api/me` → `POST /api/auth/revoke`，双形态 self-revoke + 管理员吊销），账号绑定实现应**直接按来源站身份推进**（对接形态见 [`identity-linkup-contract.md`](identity-linkup-contract.md)）。

**但本期工程上先落地方案 A**：账号绑定（site-login 令牌交换代理、跨源身份、收藏迁移）实现尚未完成，先用平台自建账号跑通 C1–C11 验收、保进度；平台账号仅作兜底，**不把它当成终态**。等到绑定实现落地，再按既定切换路径迁移，不返工。

> ⚠️ **冲突点**：[`flutter-lead-plan.md`](flutter-lead-plan.md) §8 验收表第 1 条写的是「A 的**网站账号**可登录手机与桌面，原有收藏可见」。
> 在采用平台自建过渡方案的当下，这条要改成「A 的**平台账号**可登录两端，**在平台内**新增的收藏两端可见」。否则这条验收永远无法通过。
> 「与网站收藏互通」属于后续阶段（来源站身份打通后自然成立），需要站主提供授权与 token 交换，本文不设计。

### 1.2 令牌形态：不透明令牌 vs JWT

| 方案 | 做法 | 对本阶段的影响 |
| --- | --- | --- |
| **A. 不透明令牌（推荐）** | 登录返回随机串，服务端存哈希，每次请求查库 | 可即时撤销 → C9（手机退出、桌面仍可用）天然成立；C6 切账号无残留；无需管理签名密钥 |
| B. JWT | 自包含、无状态 | 撤销要额外黑名单；「退出只结束当前会话」要靠 `jti` 列表，等于又回到查库 |

**推荐 A**。阶段 1 的请求量下，一次索引查询不是瓶颈；换来的是撤销语义干净。若 Java 侧已有 JWT 基础设施，可换 B，但**必须**额外提供「按会话撤销」的存储，否则 C9 无法通过。

### 1.3 并发写入：LWW vs 版本号冲突

**推荐 LWW（服务端最后成功提交生效）**，不做 `409 CONFLICT`。

理由：C8 只要求「最终结果符合约定的提交顺序规则」。两端同时改同一条收藏是低频场景，弹冲突框让用户二选一，成本远高于收益；而且客户端没有「合并两人意图」的 UI。响应里返回 `updated_at` 供对账与排查即可。

若 Java 侧坚持要乐观锁，需要同时改 C8 的验收表述，**这属于契约变更，必须三人确认**。

## 2. 六条铁律

1. **不用 toggle。** 收藏/取消收藏/改状态都是「声明目标状态」的幂等写请求。`POST /favorite` 这类翻转接口一遇网络重试就把用户操作反转，是跨端不一致最常见的来源。
2. **路径里永不出现 `user_id`。** 一律从令牌推导当前用户，从根上排除「改个 id 就读到别人收藏」。出现 `403 FORBIDDEN` 只作为防御，不作为正常流程。
3. **公共作品接口不带个人字段。** `GET /api/works`、`/api/works/{id}`、`/api/covers/{id}` 保持匿名可访问、可缓存；是否收藏、什么状态，一律走 `/api/me/*`。不要为了省一次请求往公共接口塞 `viewer` 字段——那会让缓存失效、也会泄露「谁在看什么」。
4. **收藏以服务端返回为准。** 客户端提交后，只有收到 2xx 且响应体的 `work_id` / `status` 与请求一致才更新界面；失败时不得显示「已同步」。
5. **取消收藏 = 删除整条记录**，状态随记录消失，不留「已取消但还是看过」的孤儿状态。
6. **写请求不自动重试。** 接口本身幂等，用户手动重试是安全的；但静默自动重试会让「失败」变成「不知道成没成」。

## 3. 数据模型

表结构、列类型、索引归 Java；这里只定**语义与唯一约束**。

> §3 描述的是**过渡期平台自建账号**的数据模型（方案 A）。目标形态——来源站身份、external_user_id、令牌只存哈希、按站点身份——见 [`identity-linkup-contract.md`](identity-linkup-contract.md)。六条工程铁律（§2）跨模型通用，不随身份模型变化。

### 3.1 账号 `account`

| 概念 | 约束 |
| --- | --- |
| `user_id` | 平台生成，客户端只当不透明字符串，**不得解析** |
| `username` | 全局唯一，登录用。大小写与空白处理由 Java 定，但必须**确定且稳定**（推荐 trim + 统一小写存储） |
| `password` | 只存哈希。算法由 Java 定，底线：**bcrypt cost ≥ 10 或 argon2id**；明文不落库、不进日志 |
| `display_name` | 可空。首期可不做，客户端回落到 `username` |

### 3.2 会话 `session`

| 概念 | 约束 |
| --- | --- |
| `token` 哈希 | 服务端只存哈希（如 SHA-256），**不存明文令牌** |
| `user_id` | 归属账号 |
| `expires_at` | 固定有效期，推荐 **30 天**；到期即失效，**不做滑动续期** |
| `revoked_at` | 退出登录时置位，只影响当前会话 |

**会话规则（直接对应 C1 / C9）**

- 一次登录 = 一条新会话，**不踢掉任何已有会话**。
- 不设「单设备登录」模式，不做互踢；清理只针对已过期会话。
- 退出登录只撤销**当前**令牌；不提供「撤销该用户全部会话」给客户端（避免误操作把另一端踢下线）。

### 3.3 收藏 `collection`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` + `work_id` | 联合唯一 | 一个用户对一部作品最多一条记录 |
| `status` | `want` / `watching` / `watched` / `null` | `null` = 已收藏但未设状态；**不是**「未收藏」 |
| `created_at` | ISO 8601 UTC | 首次收藏时间 |
| `updated_at` | ISO 8601 UTC | 最后一次状态变更或创建时间，用于对账 |

**状态语义**

- 「未收藏」= 记录不存在，不是 `status = null`。
- `status = null` 只能通过 `PATCH {status: null}` 得到（清除状态、**保留**收藏）。
- 取消收藏（`DELETE`）连记录一起删，因此**不存在**「已取消但状态还在」的中间态。

## 4. 接口清单

| # | 接口 | 认证 | 一句话边界 |
| --- | --- | --- | --- |
| ⑤ | `POST /api/auth/login` | 否 | 用户名密码换令牌；每次调用产生新会话 |
| ⑥ | `GET /api/auth/me` | 是 | 校验令牌 + 取当前用户；客户端启动时用它判断是否已登录 |
| ⑦ | `POST /api/auth/logout` | 是 | 撤销当前令牌，返回 204；其他端不受影响 |
| ⑧ | `GET /api/me/collections` | 是 | 本人收藏分页列表，可按状态过滤 |
| ⑨ | `GET /api/me/collections/{work_id}` | 是 | 单条收藏状态；**未收藏也是 200**，不是 404 |
| ⑩ | `PUT /api/me/collections/{work_id}` | 是 | 加入收藏（不存在则创建，存在则覆盖为给定状态） |
| ⑪ | `PATCH /api/me/collections/{work_id}` | 是 | **只改状态、不创建**；记录不存在 → `409 COLLECTION_REQUIRED` |
| ⑫ | `DELETE /api/me/collections/{work_id}` | 是 | 取消收藏，幂等，返回 204 |

> 认证方式：`Authorization: Bearer <token>`。**不放在 URL 查询串里**（会进访问日志与浏览器历史）。

### 4.1 `POST /api/auth/login`

```json
// 请求
{ "username": "a", "password": "..." }

// 200
{
  "token": "…43 字符base64url…",
  "expires_at": "2026-11-20T04:00:00Z",
  "user": { "user_id": "u_01H...", "username": "a", "display_name": null }
}
```

- 失败一律 `401 INVALID_CREDENTIALS`，**不区分**「用户不存在」与「密码错误」（防账号枚举）。
- 失败次数限流由 Java 定（推荐同账号 5 次/15 分钟，超限 `429 RATE_LIMITED`），但**不得**因此锁定账号。
- 明文 HTTP 仅限内网联调；生产必须 HTTPS，写进 `dev-setup.md`。

### 4.2 `GET /api/auth/me`

```json
// 200
{ "user_id": "u_01H...", "username": "a", "display_name": null }
```

令牌无效/过期 → `401 UNAUTHORIZED`。客户端在这一步失败时**只清会话，不弹错误页**（冷启动时令牌过期是正常路径）。

### 4.3 `POST /api/auth/logout`

无请求体，返回 `204`。已失效的令牌再调一次也返回 `204`（幂等，不报 401），避免客户端退出流程卡在错误分支上。

### 4.4 `GET /api/me/collections`

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `page` | 1 | 从 1 开始 |
| `page_size` | 20 | **上限 50**，超过按 50 处理（与阶段 1 一致） |
| `status` | 不传 = 全部 | `want` / `watching` / `watched`；传 `none` 表示「已收藏但未设状态」 |

```json
// 200
{
  "page": 1, "page_size": 20, "total": 37, "total_pages": 2,
  "items": [
    {
      "work_id": "W-8f3a91",
      "work_type": "anime",
      "title": "…",
      "cover_url": "http://<host>/api/covers/W-8f3a91",
      "status": "watching",
      "created_at": "2026-10-20T12:00:00Z",
      "updated_at": "2026-10-21T03:00:00Z"
    }
  ]
}
```

- **不返回 `summary`**，理由同阶段 1 列表接口：详情页才需要全文。
- `cover_url` 复用阶段 1 的封面代理规则（可空；`null` 时客户端不发请求）。
- 排序：`updated_at DESC, work_id ASC`。第二个键是为了分页稳定——**只按时间排会在同秒写入时跳条**。
- 不返回已删除的作品？作品被删时的行为本文不定（阶段 1 没有删除流程），按「不存在则不出现在列表」处理。

### 4.5 `GET /api/me/collections/{work_id}`

```json
// 200（已收藏）
{ "work_id": "W-8f3a91", "collected": true, "status": "want", "updated_at": "2026-10-21T03:00:00Z" }

// 200（未收藏）
{ "work_id": "W-8f3a91", "collected": false, "status": null, "updated_at": null }

// 404（作品本身不存在）
{ "error": { "code": "WORK_NOT_FOUND", "message": "作品不存在" } }
```

**为什么未收藏不返回 404**：详情页每次打开都要问一次状态，「未收藏」是正常结果而不是错误。若用 404，客户端会把正常状态塞进错误分支，也会让「作品不存在」与「没收藏」混为一谈。

### 4.6 `PUT /api/me/collections/{work_id}` — 加入收藏

```json
// 请求（status 可省略 = 收藏但不设状态）
{ "status": "want" }

// 200
{ "work_id": "W-8f3a91", "collected": true, "status": "want",
  "created_at": "2026-10-21T03:00:00Z", "updated_at": "2026-10-21T03:00:00Z" }
```

- **幂等 upsert**：记录不存在 → 创建；已存在 → 覆盖为给定状态。同样请求重复提交结果一致。
- 一律返回 `200`，不用 `201`：客户端不必区分「新建」与「已存在」。
- `work_id` 不存在 → `404 WORK_NOT_FOUND`。
- `status` 取值非法 → `400 BAD_REQUEST`（不要静默降级为 `null`）。

### 4.7 `PATCH /api/me/collections/{work_id}` — 只改状态

```json
// 请求
{ "status": "watched" }   // 或 { "status": null } 清除状态但保留收藏

// 200
{ "work_id": "W-8f3a91", "collected": true, "status": "watched",
  "created_at": "2026-10-21T03:00:00Z", "updated_at": "2026-10-21T04:00:00Z" }

// 409（该作品当前不在收藏里）
{ "error": { "code": "COLLECTION_REQUIRED", "message": "该作品不在收藏中，请刷新后重试" } }
```

**这是 C11 成立的唯一方式**：改状态必须用 PATCH，**绝不能**用 PUT。否则「已取消收藏的作品在过期界面被改状态」会被 PUT 静默重新收藏，C11 直接失败。

客户端对应行为：收到 `409 COLLECTION_REQUIRED` → 提示「收藏已失效，请刷新」→ 重新拉 `GET /api/me/collections/{work_id}` → 按最新状态重绘。**不自动重新提交**。

### 4.8 `DELETE /api/me/collections/{work_id}` — 取消收藏

- 返回 `204`，无响应体。
- **幂等**：记录不存在也返回 `204`（重复取消不报错，手动重试安全）。
- 删除同时清掉 `status`，因为整条记录没了。

## 5. 统一错误响应

沿用阶段 1 的信封，新增一个可选 `trace_id`（Java 决定是否提供；客户端只用于展示，不解析）：

```json
{ "error": { "code": "COLLECTION_REQUIRED", "message": "该作品不在收藏中，请刷新后重试", "trace_id": "..." } }
```

| code | HTTP | 含义 | 客户端该怎么做 |
| --- | --- | --- | --- |
| `UNAUTHORIZED` | 401 | 未登录、令牌无效或过期 | 清本地会话 → 回登录页。**不重试**，不弹错误页 |
| `INVALID_CREDENTIALS` | 401 | 登录用户名或密码错误 | 提示「账号或密码不正确」。**不要清已有会话**，不要提示「用户不存在」 |
| `BAD_REQUEST` | 400 | 参数格式错误（如 `status` 非法） | 不重试，属客户端 bug，修代码 |
| `WORK_NOT_FOUND` | 404 | `work_id` 不存在 | 提示并从收藏列表移除该条 |
| `COLLECTION_REQUIRED` | 409 | PATCH 时该作品未收藏 | 提示刷新，重新拉单条状态；**不自动重新提交** |
| `RATE_LIMITED` | 429 | 登录或写请求过于频繁 | 提示稍后再试，按 `Retry-After` 退避 |
| `INTERNAL` | 500 | 服务端错误 | 仅 GET 可自动重试一次，写请求交给用户手动重试 |

`UNAUTHORIZED` 与 `INVALID_CREDENTIALS` 都是 401，**客户端必须按 `code` 分支**，不能只看 HTTP 状态码。

## 6. 并发与幂等（C8）

| 场景 | 结果 |
| --- | --- |
| 两端同时 `PUT` 不同 `status` | 后到者生效（LWW）。先到的客户端在下次刷新时看到对方的值 |
| 一端 `DELETE`，另一端 `PATCH` | 若 DELETE 先落地 → PATCH 得到 `409 COLLECTION_REQUIRED`；若 PATCH 先落地 → DELETE 正常删掉。**两种顺序都不会产生「幽灵收藏」** |
| 同一请求因超时被用户手动重试 | 幂等，结果一致；不会出现两条记录或状态翻转 |

客户端不做本地乐观更新，因此**不需要**「冲突提示」UI；`updated_at` 只用于日志与排查。

## 7. 客户端职责（契约管不到，但验收会查）

| 项 | 要求 | 对应 |
| --- | --- | --- |
| 令牌存储 | 只存令牌，不存整个用户对象（Windows 凭据管理器单条有长度上限）。Android 走 Keystore，Windows 走 wincred，用 `flutter_secure_storage` | C6 |
| 启动流程 | 有令牌 → `GET /api/auth/me` 校验；401 则静默清会话进登录页 | C1 |
| 401 拦截 | 全局拦截器：任一请求 401 `UNAUTHORIZED` → 清会话 + `ref.invalidate` 所有 `/api/me/*` 的 provider | C6 / C7 |
| 退出登录 | 调 `POST /api/auth/logout` → 清 secure storage → invalidate 个人 provider → 清本地收藏缓存。**顺序不能反** | C6 / C9 |
| 切换账号 | 上一个账号的收藏列表、详情页状态**必须全部失效**；provider 不能带旧值（阶段 1 已踩过这个坑：Riverpod 重建会把旧值带进新状态） | C6 |
| 写请求 | 不做自动重试；收到 2xx 且响应体与请求一致才更新界面 | C7 |
| 失败表现 | 显示明确失败 + 可重试；**任何情况下不显示「已同步」** | C7 |
| 重新登录 | 数据全在服务端，登录后重新拉，不做本地缓存恢复 | C10 |

> 依赖提醒：`flutter_secure_storage` 在 Windows 上需要 VS 的 **「C++ ATL for latest v143 build tools」**。缺这个组件，桌面端直接编译不过——建议在排期前装上。

## 附录 A：内部建号接口（非客户端契约）

联调需要账号 A / B，但首期不做注册页。建议提供仅内网可用的建号接口，复用阶段 1 的 `X-Internal-Token`：

```http
POST /internal/accounts
X-Internal-Token: <内部令牌>

{ "username": "a", "password": "...", "display_name": null }
```

- `201` 创建成功；用户名已存在返回 `409` 并提供 `PUT /internal/accounts/{username}/password` 重置密码，**不做静默改密**。
- **不得**暴露给客户端，不得由 Flutter 调用。
- 若 Java 侧更愿意用 SQL 脚本建号，也完全可以——只要能造出 A/B 两个账号，本接口就不是必须的。
